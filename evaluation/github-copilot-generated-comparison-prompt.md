# GitHub Copilot Prompt — Generated Comparison JSON

Dokumen ini menyediakan dua kondisi eksperimen:

- **Mode A — frozen evidence pack**: Copilot membaca `history.json` yang sama
  dengan Historical Autodocs. Gunakan mode ini untuk perbandingan pipeline yang
  paling terkontrol.
- **Mode B — Copilot pada clone terpisah**: Copilot bekerja dari clone repository
  target dan mengambil konteks PR melalui integrasi GitHub. Gunakan mode ini
  untuk membandingkan pengalaman tool secara utuh: Historical Autodocs versus
  Copilot berbasis prompt.

## Mode A — frozen evidence pack

Gunakan prompt berikut di GitHub Copilot Agent mode. Ganti semua placeholder
`<...>` sebelum menjalankannya.

```text
You are generating a controlled evaluation candidate for a code-evolution
rationale documentation experiment.

INPUT
- Raw GitHub history file:
  storage/history-snapshots/<SNAPSHOT_ID>/history/history.json
- Snapshot ID: <SNAPSHOT_ID>
- Copilot model shown in the UI: <COPILOT_MODEL_NAME>
- Output file:
  evaluation/copilot/<SNAPSHOT_ID>-generated-comparison.json

EXPERIMENTAL ISOLATION — MANDATORY
1. Use only the raw GitHub history file specified above as the evidence source.
2. Do not read or use any file under:
   - history/evaluation/
   - history/summary/
   - evaluation/rationale-ground-truth*.json
   - any generated-comparison.json
   - any ast-with-rationale.json
3. Do not use a reference answer, silver ground truth, BERTScore result, or a
   rationale previously generated by another tool.
4. Do not browse the internet or retrieve additional repository information.
5. Create or overwrite only the requested output file.

TASK
For every issue/PR in the raw history file, generate an evidence-grounded
English rationale describing:
- the human discussion and decision, when meaningful discussion exists;
- what changed in the code; and
- why it changed, only when the reason is supported by the available evidence.

Use PR descriptions and human discussion as the primary evidence for intent,
motivation, alternatives, and decisions. Use commit messages and patches to
verify the implementation. Do not infer a definite motivation from code alone.
When evidence does not state a reason, explicitly say that the reason is not
stated instead of inventing one.

ALLOWED EVIDENCE REFERENCES
Use only IDs that can be reconstructed exactly from history.json:
- issue:<issueNumber>
- issue_comment:<commentId>
- review_comment:<commentId>
- commit:<fullCommitSha>
- patch:<fullCommitSha>:<exactFilename>

OUTPUT REQUIREMENTS
- Produce valid JSON only in the output file: no Markdown fences and no prose.
- Use the exact structure below.
- Include every issue/PR from history.json exactly once.
- Keep all issueNumber values as JSON integers.
- Keep claim IDs unique within each issue.
- Keep claims concise and atomic; avoid copying long raw patches.
- Do not optimize or rewrite the output using the evaluation ground truth.

OUTPUT STRUCTURE
{
  "snapshotId": "<SNAPSHOT_ID>",
  "repo": "<repo value from history.json>",
  "generatedAt": "<current ISO-8601 timestamp>",
  "model": "github-copilot/<COPILOT_MODEL_NAME>",
  "generator": "github-copilot",
  "generationProtocol": "controlled-raw-github-history-v1",
  "issues": [
    {
      "issueNumber": 123,
      "title": "Exact PR title from history.json",
      "generatedClaims": [
        {
          "id": "discussionNarrative:0",
          "text": "The narrative followed by its outcome in one concise claim.",
          "evidenceRefs": ["issue_comment:123456"],
          "source": "discussionNarrative"
        },
        {
          "id": "whatChanged:0",
          "text": "The code change followed by its supported rationale in one concise claim.",
          "evidenceRefs": [
            "commit:<fullCommitSha>",
            "patch:<fullCommitSha>:<exactFilename>"
          ],
          "evidenceSource": "patch_excerpt",
          "source": "whatChanged"
        }
      ],
      "discussionNarratives": [
        {
          "narrative": "Concise account of the relevant human discussion.",
          "outcome": "Decision or outcome supported by that discussion.",
          "participants": ["exact-github-login"],
          "evidenceRefs": ["issue_comment:123456"],
          "relatedCommitIds": ["<fullCommitSha>"]
        }
      ],
      "whatChanged": [
        {
          "change": "Concise description of the implemented code change.",
          "rationale": "Evidence-supported cause, effect, and solution, or a cautious statement that the reason is not stated.",
          "relatedCommitIds": ["<fullCommitSha>"],
          "evidenceRefs": [
            "commit:<fullCommitSha>",
            "patch:<fullCommitSha>:<exactFilename>"
          ],
          "evidenceSource": "patch_excerpt"
        }
      ]
    }
  ]
}

CONSISTENCY RULES
1. For each discussionNarratives[i], add exactly one generated claim with:
   - id = discussionNarrative:<i>
   - text = narrative + " " + outcome
   - the same evidenceRefs
   - source = discussionNarrative
2. For each whatChanged[i], add exactly one generated claim with:
   - id = whatChanged:<i>
   - text = change + " " + rationale
   - the same evidenceRefs and evidenceSource
   - source = whatChanged
3. Order generatedClaims as all discussionNarrative claims first, followed by
   all whatChanged claims.
4. evidenceSource must be exactly one of:
   - discussion
   - commit_message
   - patch_excerpt
   - inferred
5. Use inferred only for cautious observations and still cite the closest
   supporting commit or patch.
6. Exclude bot-only, administrative, and non-substantive conversation from
   discussionNarratives.
7. If no substantive discussion exists, return an empty discussionNarratives
   array and do not create discussionNarrative claims.
8. Do not duplicate the same fact across multiple generated claims.

VALIDATION BEFORE FINISHING
1. Parse the output as JSON.
2. Confirm the output issue numbers exactly match the issue numbers in
   history.json: no missing, duplicate, or additional issue.
3. Confirm every generatedClaims item has a non-empty unique id and text.
4. Confirm every evidence reference points to an item present in history.json.
5. Confirm generatedClaims text is derived exactly according to the consistency
   rules above.
6. If validation fails, repair the output file before finishing.

When complete, respond only with the output file path and the number of issues
written. Do not include the JSON in chat because the file may be large.
```

Setelah Copilot selesai, buka file output, salin seluruh object JSON, lalu
tempelkan ke editor **Generated comparison JSON** pada section Quantitative
Testing. Jangan berikan `ground-truth.json` kepada Copilot; aplikasi akan
menggunakan silver ground truth yang sama hanya pada tahap evaluasi.

Sebelum mengganti comparison JSON di UI, simpan raw metrics Historical Autodocs
ke file hasil terpisah. Setelah menjalankan output Copilot, simpan raw metrics
Copilot dengan nama lain. Section UI menyimpan satu hasil terakhir per snapshot,
sehingga run baru akan menggantikan artefak evaluation sebelumnya.

## Mode B — Copilot pada clone repository terpisah

Mode ini tidak membutuhkan struktur folder Historical Autodocs. Jalankan prompt
berikut dari root clone repository target. Sebelum menjalankannya, salin daftar
nomor PR yang terdapat pada silver ground truth, tetapi **jangan berikan isi
klaim ground truth kepada Copilot**. Daftar nomor PR hanya dipakai sebagai
identitas sampel uji, bukan sebagai jawaban referensi.

```text
You are GitHub Copilot running inside a standalone clone of the repository being
evaluated. Generate a controlled comparison candidate for a code-evolution
rationale documentation experiment.

EXPERIMENT CONFIGURATION
- Repository: <OWNER/REPOSITORY>
- Pull requests, in this exact order: <PR_NUMBER_1>, <PR_NUMBER_2>, ...
- Copilot model shown in the UI: <COPILOT_MODEL_NAME>
- Output file in this clone: copilot-generated-comparison.json

MANDATORY ISOLATION
1. Do not ask for, read, or use the experiment's silver ground truth, reference
   rationale, Historical Autodocs summary, Generated comparison JSON, or metric
   results.
2. Use only:
   - the current repository clone and its Git history; and
   - original GitHub PR data retrieved by Copilot's GitHub integration or an
     authenticated GitHub CLI/API available in this environment.
3. Do not use general web search, blogs, external documentation, or another AI
   system's explanation.
4. Do not modify repository source code. Create or overwrite only the requested
   output JSON file.
5. Process exactly the configured pull-request numbers. Do not add nearby PRs.

REQUIRED GITHUB EVIDENCE
For each configured PR, retrieve and inspect all of the following when
available:
- PR number, exact title, body, author, and merged state;
- issue/PR conversation comments;
- inline pull-request review comments;
- PR commits and complete commit messages;
- changed filenames and available patches/diffs.

A local Git clone does not contain GitHub discussion or review comments. If this
environment cannot access those original GitHub records, stop and report
"GitHub discussion evidence unavailable". Do not silently generate a
discussion narrative from commit messages or patches.

TASK
For every configured PR, generate concise English documentation describing:
- the relevant human discussion, alternatives, decision, and outcome, when
  substantive human discussion exists;
- what changed in the implementation; and
- why it changed, only when that reason is supported by the retrieved evidence.

Use the PR body and human discussion as primary evidence for intent, motivation,
alternatives, and decisions. Use commit messages and patches to verify the
implementation. Do not infer a definite motivation from code alone. If no
evidence states the reason, say that the reason is not stated rather than
inventing one. Exclude bot-only, administrative, approval-only, and
non-substantive comments.

EVIDENCE REFERENCE FORMAT
Use only identifiers from records actually retrieved for that PR:
- issue:<pullRequestNumber>
- issue_comment:<commentId>
- review_comment:<commentId>
- commit:<fullCommitSha>
- patch:<fullCommitSha>:<exactFilename>

OUTPUT
Write valid JSON, without Markdown fences, to
copilot-generated-comparison.json using this exact structure:

{
  "repo": "<OWNER/REPOSITORY>",
  "generatedAt": "<current ISO-8601 timestamp>",
  "model": "github-copilot/<COPILOT_MODEL_NAME>",
  "generator": "github-copilot",
  "generationProtocol": "copilot-standalone-github-context-v1",
  "issues": [
    {
      "issueNumber": 123,
      "title": "Exact PR title from GitHub",
      "generatedClaims": [
        {
          "id": "discussionNarrative:0",
          "text": "The narrative followed by its outcome.",
          "evidenceRefs": ["issue_comment:123456"],
          "source": "discussionNarrative"
        },
        {
          "id": "whatChanged:0",
          "text": "The implementation change followed by its rationale.",
          "evidenceRefs": [
            "commit:<fullCommitSha>",
            "patch:<fullCommitSha>:<exactFilename>"
          ],
          "evidenceSource": "patch_excerpt",
          "source": "whatChanged"
        }
      ],
      "discussionNarratives": [
        {
          "narrative": "Concise account of the relevant human discussion.",
          "outcome": "Decision or outcome supported by that discussion.",
          "participants": ["exact-github-login"],
          "evidenceRefs": ["issue_comment:123456"],
          "relatedCommitIds": ["<fullCommitSha>"]
        }
      ],
      "whatChanged": [
        {
          "change": "Concise description of the implemented change.",
          "rationale": "Evidence-supported reason, or a cautious statement that the reason is not stated.",
          "relatedCommitIds": ["<fullCommitSha>"],
          "evidenceRefs": [
            "commit:<fullCommitSha>",
            "patch:<fullCommitSha>:<exactFilename>"
          ],
          "evidenceSource": "patch_excerpt"
        }
      ]
    }
  ]
}

CONSISTENCY RULES
1. Include each configured PR exactly once and preserve the configured order.
2. For each discussionNarratives[i], create exactly one generatedClaims entry:
   - id = discussionNarrative:<i>
   - text = narrative + " " + outcome
   - evidenceRefs = the same evidenceRefs
   - source = discussionNarrative
3. For each whatChanged[i], create exactly one generatedClaims entry:
   - id = whatChanged:<i>
   - text = change + " " + rationale
   - evidenceRefs and evidenceSource = the same values
   - source = whatChanged
4. Order all discussionNarrative claims before all whatChanged claims.
5. evidenceSource must be exactly discussion, commit_message, patch_excerpt, or
   inferred. Use inferred only for cautious observations with nearby evidence.
6. If no substantive human discussion exists, use an empty
   discussionNarratives array and create no discussionNarrative claim.
7. Keep claims concise and atomic. Do not copy long patches and do not duplicate
   the same fact across claims.

VALIDATE BEFORE FINISHING
1. Parse the output as JSON.
2. Confirm repo exactly matches the experiment configuration.
3. Confirm the issue-number sequence exactly matches the configured PR list.
4. Confirm all generatedClaims IDs are non-empty and unique within each PR.
5. Confirm every evidence reference resolves to a retrieved GitHub record.
6. Confirm generatedClaims text exactly follows the consistency rules.
7. Repair the output before finishing if any validation fails.

When complete, respond only with the output path, model name, and number of PRs
written. Do not paste the large JSON into chat.
```

Setelah selesai, pindahkan atau salin `copilot-generated-comparison.json` ke
editor **Generated comparison JSON** pada snapshot yang sesuai. Evaluator akan
membandingkannya dengan silver ground truth yang sama tanpa pernah memperlihatkan
ground truth tersebut kepada Copilot.

Mode B menguji tool secara end-to-end, tetapi sumber inputnya tidak identik
secara byte dengan Historical Autodocs karena Copilot mengambil ulang data dari
GitHub. Catat waktu pengambilan, model Copilot, daftar PR, dan ketersediaan
discussion sebagai variabel eksperimen. Untuk klaim perbandingan pipeline yang
benar-benar terkontrol, gunakan Mode A.
